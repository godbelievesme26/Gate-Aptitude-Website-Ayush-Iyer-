# Visual design audit — GATE Aptitude

**Date:** 4 October 2026  
**Scope:** Audit and design direction for an existing commercial study product. This pass changes documentation only. It does not change question content, state, scoring, routes, controls, or screen layouts.

## What was inspected

- The application is a static, framework-free HTML/CSS/JavaScript app. `index.html` loads four stylesheets in order: `style.css`, `quiz.css`, `system.css`, and `components.css`. `app.js` owns the hash router, navigation shell, and delegated actions. `home.js`, `views.js`, and `ui.js` return HTML strings. State and content live separately in `state.js`, `storage.js`, and `loader.js`.
- Source review covered all route renderers, the shared shell, token layers, quiz stylesheet, control and surface utilities, error/loading/empty markup, responsive media queries, and reduced-motion handling.
- Live visual inspection covered dark-theme Home, question bank, and question detail at desktop size, plus Home and bank at a **390 × 844** mobile viewport. The desktop screenshots showed the whole shell and first fold; the mobile screenshots showed the initial viewport. Accessibility trees were checked on those routes.
- The active quiz and its answer/feedback states were inspected in HTML/CSS and render tests. They were **not** opened live because starting a session would write to the user's saved progress. Tablet pixels, light-theme pixels, modal/open-menu pixels, screen-reader behavior, and corrupted-state visuals were **not** live verified. Findings for those areas are explicitly source-based.
- Baseline checks: **66/66 tests passed**, JavaScript syntax passed, and the data validator passed for **16 sets / 160 unique questions**. The supplied papers do not include verified answer keys or solutions; that is a content limitation, not a visual defect.

## Executive diagnosis

The product is orderly and credible, but its composition still resembles a productivity dashboard more than a premium learning environment. The fixed sidebar, top utility bar, repeated compact panels, boxed lists, metrics, badges, and small metadata give most pages the same visual cadence. Very different moments—choosing a study session, reading an exam question, reviewing history, changing settings—receive similar bordered surfaces and control density. The hierarchy is therefore driven by containers rather than by the student's task.

The first impression is especially affected by the number of visible interface objects. The desktop Home first fold has a sidebar CTA, top search/XP/avatar utilities, a recommendation panel, a second goal panel, four stats, and a review list. The recommendation is clear, but the surrounding dashboard signals compete for attention. On the bank, every result is a large bordered card even though a scannable list would carry the information. On question detail, six actions precede the source question. These are specific reasons it feels administrative and static, rather than simply a matter of color or roundness.

## Findings by dimension

| Area | Current evidence | Effect on perceived quality | Direction |
| --- | --- | --- | --- |
| **A. First impression** | Home asks “What should I do right now?” and presents Start now with time and estimate. Desktop also exposes XP, level, goal, four stats, journey, review links, and history. | The core action is understandable; surrounding dashboard furniture reduces its emotional priority. | Keep one dominant study decision. Use calm supporting text and progressive detail below the fold. |
| **B. Premium perception** | Palette is restrained; there is no neon or decorative gradient. But the same panel/border language repeats across daily sets, bank, settings, analytics, and detail. | Polished consistency is present, but sameness and density make it feel like a generic admin interface. | Build distinction through composition, reading measure, and task-specific hierarchy, not decoration. |
| **C. Typography** | Georgia titles and Segoe UI body are a credible pair. Body is 1rem/1.6, but captions and navigation labels are often 0.75–0.8125rem; nav-group labels are 0.6875rem. Source paper text is raster imagery. | Large headings feel academic; essential metadata can feel miniaturized. Serif display has little influence beyond headings. | Set a minimum practical size for task-critical secondary text, establish reading widths, and reserve serif for deliberate editorial moments. |
| **D. Spacing** | A token scale exists, but `style.css`, `quiz.css`, and inline styles retain many direct values. Home uses a 40px desktop gutter; question detail uses 24px panel gaps and a dense six-button strip. | Relationships vary subtly; whitespace is often inside boxes rather than between ideas. | Apply a small layout rhythm by relationship: page, section, text/control, dense data. |
| **E. Hierarchy** | Home's recommendation is most prominent. Bank results use similar card weight; question detail actions appear before the source image. The quiz markup puts question before response and Continue/Submit, then support. | The product knows what matters but does not consistently show it. | On each route, identify the single primary task and suppress competing chrome. |
| **F. Color** | Light canvas `#f4f5f7`, dark canvas `#15171c`, indigo accent, semantic success/warning/error tokens. Accent also appears in nav, progress, pills, links, and actions. | Color is calm, but indigo can become a generic “everything interactive” signal. Dark-theme borders carry much of the structure. | Reserve strongest accent for a decision/current state; rely on typography and spacing for lower-priority grouping. Check contrast per role in both themes before rollout. |
| **G. Surfaces/cards** | Existing utilities define plain, subtle, elevated, bordered, emphasis. Existing `.panel` remains widely used; bank rows and detail subsections are boxed; quiz has a panel around a white source-image frame and another support panel. | Border-on-border and card-within-card make reading feel framed and busy. | Reduce the practical hierarchy to open canvas, subtle grouping, and primary interactive surface. Treat border/elevation/emphasis as modifiers. |
| **H. Radius** | Controls use 6px, panels 9px, dialogs 12px; source frame and data rows use nearby independent values. | Appropriate restraint; small inconsistencies are visible across repeated components. | Keep a compact radius scale and use shape to indicate function, not novelty. |
| **I. Buttons/inputs** | Native controls have 44px base minimums and visible focus. Primary, secondary, ghost, destructive, selected, disabled, loading styles exist in `components.css`. The broad base `button` rule applies to every context. | Behavior is credible, but the many adjacent same-sized buttons on question detail flatten priority. Hover/selected treatment is partly dependent on cascade order. | Define usage rules per task, then visually audit the active, hover, pressed, disabled, and busy states in both themes. |
| **J. Navigation** | Study/Review/Progress groups, clear route labels, consistent outline icons, and a sidebar Start action. The 230px fixed rail persists on desktop; the top bar repeats search, level, XP, theme, avatar. | Reachability is good; the permanent rail and utility bar add an admin-shell feel. | Keep destinations, but reduce chrome near the solving surface and clarify which utility information deserves persistent visibility. |
| **K. Question experience** | Source paper is an image in a white frame, with a separate response section. In the quiz template the question precedes answer controls and the action. At widths below 900px, `.quiz-aside` is reordered ahead of the question. | The authentic source is trustworthy, but the paper crop can visually dominate through its white rectangle and fixed image typography; at tablet/mobile the support panel may precede the question. | Preserve the authentic source; make its reading space dominant and keep answer/action close. Test actual quiz pixels and mobile order in the next phase. |
| **L. Answer options** | Current quiz choices are A–D letter buttons in a four-column grid (two on compact screens); the full option text remains in the source image. Selected state is shown via CSS and `aria-pressed`. | Tappable and concise, but the separate letter controls and raster answer text require eye travel. | Later prototype a refined choice treatment that preserves the real source and existing answer actions; validate text extraction before changing how options appear. |
| **M. Feedback states** | Result feedback is concise and uses a live status region. Missing answer keys are described honestly. `correct` has a small CSS confirmation animation; notices and errors have text plus semantic color. | Wording earns trust; visual distinction and recovery hierarchy need live assessment. | Use text first, semantic color second, with one next action. Test keyed, ungraded, blank, and failure states with fixtures. |
| **N. Motion** | `components.css` defines 120ms control motion, 180ms view entry, a loading pulse, and reduced-motion overrides. It is already restrained. | The product is not overanimated, but transitions are not yet tied to a complete state inventory. | Keep motion under the interaction pace; only animate state changes that help continuity. Avoid repeating entry motion on data-only rerenders. |
| **O. Responsive** | At 390px, Home and bank fit without document-width overflow; sidebar is hidden and exposed through a menu button. Filters wrap into two-column and stacked rows. Mobile Home becomes a long single-column page. Tablet uses a narrower persistent sidebar (source review). | Functional but still a compressed dashboard; mobile information order and long scroll need purpose-built treatment. | Design a distinct compact hierarchy, especially question → choice → action → support. Verify 768px and small-height devices in the redesign phase. |
| **P. Accessibility** | Skip link, named nav, labeled icon-only controls, `:focus-visible`, native form elements, reduced-motion rule, live status areas, and descriptive source-image alt text are present. The 118-day grid includes 102 unavailable cells exposed with labels. | Strong baseline, but dense low-priority announcements, small metadata, and unverified mobile-menu focus behavior may make long use tiring. | Preserve semantics; test keyboard route, focus return, contrast, zoom, and screen reader verbosity as acceptance criteria. |
| **Q. Consistency** | Four stylesheets layer legacy declarations, quiz overrides, tokens, and components. Many `views.js` templates contain inline spacing. Some semantic roles exist as tokens but not usage rules. | The system is centralized in name more than in application; future redesigns could drift. | Consolidate adoption route by route after prototype approval; do not bulk-replace CSS in this audit. |

## What works and should survive

- Honest content provenance: original question crops remain visible, and unavailable keys/solutions are stated plainly.
- A clear Home start path, source-backed bank, persistent progress, and all existing destinations.
- A mature accessibility foundation: native controls, keyboard reachability, focus indication, skip navigation, and reduced-motion support.
- A restrained, calm color family and moderate radii. The product does not need a new visual gimmick.
- Separation of actual question content and personal notes/review material.

## Highest-impact issues to solve next

1. **Question reading and answer composition.** It is the product's core paid experience and currently combines a panel, a white source frame, a support panel, and separate letter controls. Validate the active session visually before altering it.
2. **Too many equivalent containers.** Bank cards, daily set cards, analytics panels, and detail sections use similar borders and padding. Reserve the strongest surface for an actual decision or interactive unit.
3. **Small but frequent metadata.** Increase task-relevant secondary text size and improve line length; do not enlarge every label equally.
4. **Persistent utility density.** XP, level, search, avatar, sidebar CTA, and multiple secondary paths all appear before the question. Reduce their visual weight in solving contexts while keeping them reachable.
5. **CSS adoption drift.** Token values are present, but direct values and inline styles still drive several routes. Refactor incrementally with screenshot and accessibility checks.

## Verification limits

This is a visual and architectural audit, not a usability study or market test. It does not prove a pricing response or conversion rate. The live visual findings are strongest for dark-theme Home, bank, and question detail. Active quiz, light theme, tablet layout, focus-mode pixels, and feedback states remain priorities for visual verification when their redesign begins.
